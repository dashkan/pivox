# AI Chat — macOS Frontend Implementation Plan

Scoped to the macOS AI Chat feature: how the native SwiftUI app consumes the Go BE (`docs/ai/backend-plan.md`) via the `PivoxModels` SPM package.

**Not in scope**:
- The full `AIElements` component library (`docs/ai/plan.md`)
- WinUI port (handoff from `docs/ai/plan.md` M6)
- Go backend (`docs/ai/backend-plan.md`)

## History note

This plan originally specified a shared C++ `AiChatClient` library reached over a Swift↔C++ interop bridge, with three custom protoc plugins (`protoc-gen-pivox-cpp-bridge`, `protoc-gen-pivox-swift-facade`, `protoc-gen-pivox-swift-protobridge`) producing the FFI seam. That entire layer was retired in favor of pure Swift gRPC via `grpc-swift-2`. The macOS app talks to the cloud directly; there is no shared C++ chat-client core. WinRT will need its own native gRPC client when that work begins — nothing the macOS rewrite produced is reusable there.

## TL;DR

- **Feature placement**: dedicated AI Chat sidebar entry in the SwiftUI app. Inline-in-context use is later work.
- **Proto types + gRPC stubs**: consumed via the `PivoxModels` SPM package. Generated by `apple/swift-protobuf` (proto types) + `protoc-gen-grpc-swift-2` (gRPC client stubs). Single `import PivoxModels` for everything.
- **Transport**: `grpc-swift-2` HTTP/2 (`HTTP2ClientTransport.Posix`). `ChatClient` (Swift) wraps the generated `Pivox_Ai_V1_AiChat.Client` and runs the connection lifecycle. Bidi stream usage is currently `streamGenerateContent` (server-stream of `ServerEvent`).
- **Auth**: `FirebaseAuthInterceptor` (a `grpc-swift-2` `ClientInterceptor` inside `ChatClient.swift`) attaches `authorization: Bearer <id_token>` per RPC. Tokens come from `Auth.auth().currentUser?.getIDToken()`; Firebase manages refresh. No global registration, no bridge.
- **Storage session**: Swift calls `StorageGateways.CreateStorageSession` once after Firebase login → `pivox_session` cookie set on `.pivox.app` → asset/gateway fetches via `AsyncImage` work transparently.
- **Conversation state**: server-authoritative. Client reads via the AIP resource RPCs (`ListConversations`, `GetConversation`, `ListMessages`); new turns flow over `streamGenerateContent`. No local shadow of history beyond view state.
- **Tool machinery**: end-to-end wiring is defined in the proto. Tool registry is empty in v1 — adding a tool is a registration call, not a feature.
- **Artifact rendering**: inline-only in v1 (code, markdown, svg). Asset-backed artifacts and image generation are deferred.
- **Token counting / history**: server-side only. Swift renders what each turn produces.
- **Testing**: TDD throughout — XCTest for unit/logic, `swift-snapshot-testing` for SwiftUI views, XCUITest for feature flows.
- **Swift version**: Swift 6 language mode, strict concurrency complete. C++ interop is **not** enabled — there is no C++ to interop with for chat.

## Architecture

Two layers:

```
┌──────────────────────────────────────────────────────────────┐
│  SwiftUI app code (native/platform/macos/swift/AIChat/)      │
│  - Sidebar entry, conversation list, chat view               │
│  - Consumes AIElements for Message / PromptInput / etc.      │
│  - Uses typed proto values from PivoxModels                  │
│  - Holds `ChatClient` via AIChatService                      │
└──────────────────────┬───────────────────────────────────────┘
                       │ typed Swift API
                       │ async / AsyncThrowingStream
                       ▼
┌──────────────────────────────────────────────────────────────┐
│  ChatClient (PivoxModels-backed, grpc-swift-2 native)        │
│  - HTTP2ClientTransport.Posix                                 │
│  - Wraps generated `Pivox_Ai_V1_AiChat.Client`                │
│  - FirebaseAuthInterceptor attaches Bearer token per RPC      │
│  - runConnections() task lives for the client's lifetime      │
└──────────────────────┬───────────────────────────────────────┘
                       │ HTTP/2 (TLS in prod, plaintext in dev)
                       ▼
              Go `pivox.ai.v1.AiChat` service
              (docs/ai/backend-plan.md)
```

## Phases

### Phase 0 — Foundations ✅

`PivoxModels` SPM package + `swift build` integration. SwiftPM resolves grpc-swift-2 + transitive C deps (BoringSSL via swift-nio-ssl); CMake imports the resulting `libPivoxModels.dylib` and embeds it under `Contents/Frameworks/`.

### Phase 1 — `ChatClient` ✅

Single Swift file (`AIChat/Client/ChatClient.swift`) that:
- creates an `HTTP2ClientTransport.Posix` channel pointed at the cloud endpoint
- wraps the generated `Pivox_Ai_V1_AiChat.Client`
- registers a `FirebaseAuthInterceptor` (`ClientInterceptor`) that pulls the current user's ID token from `Auth.auth().currentUser?.getIDToken()`
- exposes typed `async`/`AsyncThrowingStream` methods per RPC: `listConversations`, `getConversation`, `createConversation`, `updateConversation`, `deleteConversation`, `summarizeConversation`, `listMessages`, `streamGenerateContent`
- runs the gRPC connection task in the background and tears it down on `cancel()`

### Phase 2 — App-lifetime owner ✅

`AIChatService` is an `@Observable @MainActor` singleton that:
- creates the `ChatClient` once after sign-in and keeps it alive across panel re-mounts (dock ↔ detach)
- caches one `ConversationViewModel` at a time so re-mounts re-attach to the same in-flight stream
- exposes `connect()`, `viewModel(for:)`, `reset()`

### Phase 3 — Conversation list + chat view ✅

`ConversationListViewModel`: lists/creates/deletes/updates conversations.
`ConversationViewModel`: loads message history, sends new messages, drives the streaming response. View layer composes `AIElements` Message / PromptInput / etc.

### Phase 4 — Tool dispatch (deferred)

The streaming protocol carries tool calls; client tool dispatch loop is not yet wired. Adding a tool registry + execution surface is the v1.x deliverable. Server-side tool execution (Go backend) is already in place.

### Phase 5 — Artifact rendering polish (deferred)

Inline code/markdown/svg via AIElements is functional. Asset-backed artifacts and image generation render through the storage session cookie path; both are post-v1.

## Non-goals / explicit deferrals

- **Multi-org switching at runtime**: `AIChatService.orgName` is a hardcoded `"local-corp"` until org-membership lookup lands.
- **Client-side token budgeting**: server-side only.
- **Local conversation cache**: server is authoritative; no SQLite shadow.
- **Bidirectional streaming RPC for chat**: current usage is server-stream only (`streamGenerateContent`). Bidi (e.g. interactive tool calls) is future work.

## What this plan no longer covers

- Shared C++ `AiChatClient` library (deleted with the bridge retirement)
- C FFI seam (`chat_client_c.h` / Swift's `OpaquePointer` wrapper) — no longer exists
- Three custom protoc plugins (`cpp-bridge`, `swift-facade`, `swift-protobridge`) — deleted; `protoc-gen-grpc-swift-2` from grpc-swift-protobuf does the codegen
- WinUI port reuse from a shared C++ core — Windows will write its own native gRPC client when that work begins
